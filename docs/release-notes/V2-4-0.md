# Panacea v2.4.0 — Release Notes

**Release Date:** June 26, 2026

## What's New

### 1. Single Retry Mechanism

**What it does**

After the main test run completes, any test that ended with a `FAIL` or `CRASH` is automatically re-executed once on the same browser or device it originally ran on. The final summary and ALM all reflect the last known result — not the first.

**Why it's useful**

Flaky tests (network blips, timing issues, device hiccups) no longer cause false failures in your pipeline. A test that was genuinely flaky recovers automatically. A test that is truly broken will still fail — the retry confirms it.

**How to enable**

Add one line to the config dict in your project's `runner.py`:

```python
config = {
    "ALM": False,
    "TERMINAL_LOG": False,
    "LOG_LENS": False,
    "AWS_S3": False,
    "OPENSEARCH": False,
    "RETRY_FAILURES": True,  # ← add this
}
```

Leave it out or set it to `False` to keep the existing behaviour unchanged.

**How it works**

**Web:**
```
Main run  → tests execute across browsers
          → PANACEA-101 FAIL on chrome
          → PANACEA-102 PASS on firefox
Retry     → PANACEA-101 re-queued on chrome (same browser, pinned)
          → PANACEA-101 PASS ✓
```

**Mobile:**
```
Main run  → tests execute across devices
          → PANACEA-201 CRASH on Pixel_7
          → PANACEA-202 PASS on Samsung_S24
Retry     → PANACEA-201 re-runs on Pixel_7 (same device, pinned)
          → PANACEA-201 PASS ✓
```

**General vs. Specific tests**

- **Specific tests** (pinned to a browser/device in `test_execution.yaml`) always retry on the same browser/device they are pinned to.
- **General tests** (no pin) retry on whichever browser/device they originally ran on — that information is captured automatically from the run results.

**Results folder**

Each retry produces a separate folder with a `_retry` suffix so original failure evidence is never lost:

```
TestResults/
  22-06-26_10-00-00/
    chrome/
      LoginSuite/
        PANACEA-101/         ← original run (FAILED)
        PANACEA-101_retry/   ← retry run (PASSED)
        PANACEA-102/         ← original run (PASSED, no retry)
```

**Summary output**

The execution summary gains a **Retried** count when at least one test was retried. All other counts (Passed, Failed, Crashed) reflect the final result only.

```
======================================================================
 TEST EXECUTION SUMMARY
======================================================================
 Total         : 10
 Passed        : 9
 Failed        : 1
 Crashed       : 0
 Not Executed  : 0
 Retried       : 2
======================================================================
```

**What does NOT change**

- Browser slot manager — same slots, same concurrency
- ALM — updated naturally by the retry run (status goes `EXECUTING` → `PASSED`/`FAILED`)
- Log Lens, S3, OpenSearch — pick up retry folders automatically
- Everything is opt-in — default behaviour is unchanged

### 2. Secret Data Masking

**What it does**

Sensitive values (passwords, tokens, API keys) are kept out of your repository entirely. They live in a `.env` file at your project root and are referenced symbolically inside your config files. Panacea resolves them at runtime and automatically masks them in all Robot Framework logs and reports.

**Why it's useful**

- Secrets never appear in source code or Git history
- If a secret value accidentally leaks into a log line, Panacea masks it as `***`
- Each team member or CI pipeline can have its own `.env` with different credentials
- Works across any YAML (`.yaml`) or JSON (`.json`) file inside `ConfigFiles/`, including `testdata.yaml`, environment configs, API configs, and any other data files

**How to use**

**Step 1 — Create a `.env` file in your project root**

```
TEST_USERNAME=john.doe@company.com
TEST_PASSWORD=SuperSecret123
API_TOKEN=eyJhbGciOiJSUzI1...
```

:::note
Add `.env` to your `.gitignore` — it should never be committed.
:::

**Step 2 — Reference secrets using `${ENV:VAR_NAME}` in any YAML or JSON file inside `ConfigFiles/`**

In `ConfigFiles/testdata.yaml`:
```yaml
login_data:
  username: "${ENV:TEST_USERNAME}"
  password: "${ENV:TEST_PASSWORD}"
```

In `ConfigFiles/api_config.json`:
```json
{
  "api_token": "${ENV:API_TOKEN}"
}
```

In `ConfigFiles/environment.yaml`:
```yaml
base_url: "https://staging.example.com"
auth_header: "${ENV:API_TOKEN}"
db_password: "${ENV:DB_PASSWORD}"
```

Any `.yaml` or `.json` file placed inside `ConfigFiles/` supports `${ENV:VAR_NAME}` — no additional setup is needed per file.

**Step 3 — Load data using Panacea's DataLoader**

Import DataLoader as a library in your Robot Framework resource file. It handles resolution and masking automatically for any YAML or JSON file in `ConfigFiles/`.

```robotframework
*** Settings ***
Library    CommonUtils.dataloader.DataLoader

*** Keywords ***
Load Test Config
    # Load the entire file as a dictionary
    ${all_data}=    Get All Data From File    ConfigFiles/testdata.yaml

    # Load a specific section from a YAML or JSON file
    ${login_data}=    Get Section From File    ConfigFiles/testdata.yaml    login_data

    # Load a single value — section → key
    ${username}=    Get Value From File    ConfigFiles/testdata.yaml    login_data    username

    # Works identically for JSON files inside ConfigFiles/
    ${api_cfg}=    Get All Data From File    ConfigFiles/api_config.json

    # All resolved values are automatically masked in Robot Framework logs
    RETURN    ${login_data}
```

**From the UI**

Secrets can also be configured and masked directly from the Panacea UI without touching any file manually.

### 3. ZmxApiLibrary — New Validation Keywords

**What's new**

ZmxApiLibrary now ships with a dedicated set of validation keywords for asserting response body content, headers, JSON structure, and response time directly in your Robot Framework test cases.

**New keywords**

**Response body**

| Keyword | What it does |
| --- | --- |
| Response Should Contain | Asserts the response body contains a given string |
| Response Should Not Contain | Asserts the response body does NOT contain a given string |
| Response Should Be JSON | Asserts the response is valid JSON; returns the parsed object |

**Headers**

| Keyword | What it does |
| --- | --- |
| Response Header Should Exist | Asserts a header is present (case-insensitive) |
| Response Header Should Equal | Asserts a header matches the expected value |

**JSON body inspection**

| Keyword | What it does |
| --- | --- |
| Get JSON Value | Extracts a value using dot notation (`user.name`, `items.0.id`, `$.auth.token`) |
| JSON Value Should Equal | Asserts a JSON path value equals expected |
| JSON Value Should Not Equal | Asserts a JSON path value does NOT equal expected |
| JSON Value Should Contain | Asserts a JSON path value contains a substring |
| Response JSON Should Contain Key | Asserts the top-level JSON object contains a key |
| JSON Array Length Should Be | Asserts an array at a JSON path has the expected length |
| JSON Array Should Not Be Empty | Asserts an array at a JSON path has at least one item |

**Status & performance**

| Keyword | What it does |
| --- | --- |
| Response Status Should Be In | Asserts the status code is one of several acceptable values |
| Response Time Should Be Less Than | Asserts response time is under N milliseconds |

**Logging**

| Keyword | What it does |
| --- | --- |
| Log Response Body | Pretty-prints the full response body to the RF log |

**Example usage in a `.robot` file**

```robotframework
*** Settings ***
Library    ZmxApiLibrary

*** Test Cases ***
Validate Login API
    ${response}=    POST    https://api.example.com/login    json={"user": "test@example.com"}
    Response Should Be JSON    ${response}
    Response JSON Should Contain Key    ${response}    access_token
    Response Header Should Equal    ${response}    Content-Type    application/json
    Response Time Should Be Less Than    ${response}    2000
    ${token}=    Get JSON Value    ${response}    access_token
    JSON Value Should Contain    ${response}    user.email    @example.com
    Response Status Should Be In    ${response}    200    201
```

### 4. API Test Execution Support

**What it does**

Panacea runner now supports executing REST API test suites directly — alongside the existing web and mobile execution modes.

**How `test_execution.yaml` looks for API tests**

```yaml
api: rest
testsuite:
  - DummyJsonDemo/TestSuites
robot_files:
  - 01_Auth.robot
  - 02_Users.robot
  - 03_Products.robot
```

- `api: rest` tells Panacea this is an API execution (no browsers or devices needed)
- `testsuite` points to the folder containing your `.robot` files
- `robot_files` lists which files to run — omit it to run all `.robot` files in the suite
- `specific_tests` is not supported for API type — remove it if present

**Key difference from web/mobile**

API tests run sequentially in a single process — there are no parallel workers or slot managers. Everything else (ALM, S3, OpenSearch, log processing) works exactly the same.

### 5. Playwright Migration — BrowserTestLibrary

**What's new**

Panacea web automation is now fully migrated to Playwright for faster and more reliable browser execution. BrowserTestLibrary now runs entirely on Playwright while keeping the same keyword-driven experience — no changes needed to your existing `.robot` files.

**Browser support**

Out-of-the-box support for:
- Chromium
- Firefox
- WebKit

**Removed**

- Selenium-based web automation has been completely removed
- Playwright is now the default and only supported engine for all web testing in Panacea

**Action required**

- No keyword changes needed — BrowserTestLibrary keywords remain the same
- After installing the Panacea `.whl`, run:

```bash
panacea install browsers
```
